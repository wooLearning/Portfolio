검증 방식

  • sequence가 directed/random transaction 생성
  • driver가 virtual interface로 DUT 구동
  • monitor transaction을 scoreboard와 coverage로 전달
  • RAM/FIFO는 protocol assertion 추가

Adder에서 달라지는 점

  • clocking block 없이 조합 settle 후 sample
  • scoreboard reference model은 상태가 없는 즉시 계산
  • coverage는 입력 corner와 carry 발생 여부 중심

RAM UVM Class 구조

RAM에서 필요한 처리

  • driver는 clocking block으로 command 유지
  • monitor는 read command 이후 갱신된 oRData sample
  • scoreboard는 reference memory 상태 유지

interface SVA

  • selected transaction에서 X/Z control 방지
  • write data known check
  • reset 중 command idle check

FIFO UVM Class 구조

FIFO에서 필요한 처리

  • read data는 edge 직전 old rd_ptr 기준으로 확인
  • scoreboard는 full/empty를 이용해 fire 여부 계산
  • count/full/empty consistency assertion 사용

blocked request

  • full 상태 write는 push하지 않음
  • empty 상태 read는 pop하지 않음
  • valid write/read 동시는 count 유지

FIFO Sequence / Scoreboard / Coverage

sequence 구성

구간내용

wr_fire = iWrEn && !oFull rd_fire = iRdEn && !oEmpty if (rd_fire) compare(model_q.pop_front(), oRdData) if (wr_fire) model_q.push_back(iWrData)

coverage bins

  • cp_cmd: idle/write/read/wr_rd
  • cp_count: zero/mid/full
  • cross_cmd_status

결론

최종 정리

Adder, RAM, FIFO는 동일한 UVM testbench 골격을 공유하지만, 실제 검증 품질은 DUT별 timing rule, reference model, coverage 목표를 분리했을 때 확보된다.

구조 재사용

  • test / env / agent / sequence 구조를 세 DUT에 동일하게 적용
  • factory 기반 class 생성 흐름과 connect 구조 확인

모델링 차이

  • Adder는 즉시 계산 reference model 사용
  • RAM은 model_mem, FIFO는 model_q로 상태 유지

검증 증거

  • Verdi waveform으로 pin-level timing 확인
  • UVM report와 coverage 화면으로 scenario 수행 결과 확인
구분이번 실습에서 확인한 점추가 개선 방향
Sequencedirected case와 random case를 함께 구성constraint 분리, corner regression 확대
